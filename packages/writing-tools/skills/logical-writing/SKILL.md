# 논리적인 글쓰기

목표는 정보를 많이 담는 것이 아니라 독자가 결론을 이해하고 근거에 따라 판단하게 하는 것이다. 주제와 문서 형식에 맞게 적용한다.

## 핵심 규칙

1. **독자부터 정한다.** 독자가 무엇을 판단해야 하는지 한 문장으로 쓴다. 필요한 배경을 모른다고 가정하되 독자의 실제 전문성과 요구를 반영한다.
2. **문장의 포함 기준을 적용한다.** 뒤의 설명에 필요한가, 독자의 판단에 필요한가? 둘 다 아니면 뺀다. 불필요한 절차 준수 확인, 방어적 단서, 내부 사정, 결론과 무관한 시행착오는 덜어낸다. 판단을 바꾸는 경고·제약·한계는 남긴다.
3. **문장보다 구조를 먼저 정한다.** 결론 한 문장 → 소수의 핵심 논점 → 근거 순서로 잡는다. 단락마다 뒷받침하는 논점을 밝힌다. 분류의 이유와 겹침·누락을 확인하고, 맞지 않는 사례를 억지로 끼우지 않는다. 좋은 사례의 내용이 아니라 구성을 빌린다. 흐름 밖의 상세 절차와 표는 부록으로 보낸다.
4. **왜 → 어떻게 → 그래서를 잇는다.** 관측과 확인 방법 → 원인 후보의 구분 → 가설과 행동의 연결 → 결과와 설명 → 다음 판단을 쓴다. 실행 전 제안은 결과 대신 검증 계획을 밝힌다. 비교에는 기준 대상, 바꾼 조건, 고정한 조건, 판단 기준을 붙이고, 선택한 조건만이 아니라 조건별 결과를 함께 제시한다. 핵심 비교가 한눈에 보이도록 표나 그래프를 쓴다. 결과의 원인 설명은 근거가 허용하는 범위로 한정하고, 결과를 본 뒤 추가한 분석은 최초 설계와 구분한다.
5. **흐름과 주장의 범위를 지킨다.** 새 개념은 필요성과 뜻을 먼저 소개한다. 동기가 행동을 실제로 뒷받침하는지 확인한다. 서로 다른 가설은 각각의 근거로 판단한다. 지표가 높거나 낮다는 말에는 왜 독자의 판단에 중요한지 붙인다.
6. **용어와 수치를 구체화한다.** 분야의 표준 용어를 확인하고 첫 등장에 정의한 뒤 통일한다. 원어가 더 명확하면 원어를 쓴다. 수치에는 측정 대상·분자·분모·단위를 밝히고, 서로 다른 집합을 부분과 전체처럼 쓰지 않는다. 모호한 지시어를 실체로 바꾸고, 주어·행동·조건·결과를 드러내며 한 문장에는 한 내용을 담는다.
7. **근거의 종류를 구분한다.** 선택과 분석마다 독자가 검토할 수 있는 이유, 방법의 타당성, 수행 조건을 남긴다. 작업 중에는 **[확인된 사실] / [사후 근거] / [추정] / [근거 없음]**으로 구분한다. 최종 문서의 표기 형식은 독자와 형식에 맞추되 차이는 유지한다. 이유가 기록에 없으면 조사한 뒤 사후 근거임을 밝힌다. 못 찾으면 근거 없음으로 남기고 필요한 확인을 요청한다. 출처를 직접 열어 내용을 확인하기 전에는 인용하지 않는다. 사실은 원자료까지 추적하고 이후 반증·수정도 확인한다.
8. **분석을 명제로 추상화한다.** 결과를 나열하지 말고 독자의 판단에 기여하는 핵심 명제로 묶는다. 행동을 제안한다면 무엇을 왜 바꿀지 연결한다. 결론에 중요한 전제는 원자료로 뒷받침하고, 기존 산출물의 중요한 통찰과 반례를 빠뜨리지 않는다.

## 작성·검토 절차

독자와 판단 기준 → 결론·논점·순서 → 각 논점의 왜·어떻게·그래서 → 근거 확인 → 문장별 포함 판정 → 용어·수치·문장 정리 → 맥락 없는 독자에게 읽히기 순서로 진행한다. 여러 조사자(사람이든 에이전트든)와 근거를 모을 때는 영역별로 보고서를 쓰게 하고, 조사하지 않은 별도 검토자가 출처의 실재·수치·원문 대조를 마친 뒤에 근거 종류를 구분해 종합한다. 독자 테스트에서는 결론을 어떻게 이해했는지, 어디서 막혔는지, 무엇을 추측해야 했는지 묻는다. 수정은 구조와 논리의 문제부터 하고 표현은 마지막에 다듬는다.

## 참고 자료를 읽는 시점

- 최종 검토나 검토 요청에는 [퇴고 체크리스트](references/checklist.md)를 읽는다.
- 추상 규칙만으로 수정 방향이 안 보이거나 피드백을 해석할 때는 [합성 피드백 사례](references/feedback-cases.md)를 읽는다.
- 사실 검증·문장 스타일·문서 형식 등 다른 작업과 역할을 나눌 때는 [관련 역량](references/related-skills.md)을 읽는다.
- 피드백을 기록하거나 이 skill을 개선할 때는 [피드백 로그](references/feedback-log.md)를 읽는다. 반복되는 교훈은 핵심 규칙으로 승격하고, 사용자에게 보이는 변경에는 패키지의 changelog fragment를 추가한다.
