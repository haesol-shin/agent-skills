# 피드백 로그와 규칙 개선

피드백을 새로 기록하거나 skill을 수정할 때 읽는다. 원문 피드백이나 실제 문서 발췌를 복사하지 않는다. 식별 정보를 가리는 데 그치지 말고, 교훈만 남긴 별개의 합성 상황과 문장으로 다시 만든다. 실제 인물·조직·과목·프로젝트 식별자, 개인 정보, 비공개 시설·도구, 로컬 파일 경로, 원자료는 기록하지 않는다.

## 기록 형식

새 항목에는 아래 필드를 쓴다. 날짜는 기록 날짜이며 합성 사례의 관측 날짜가 아니다.

- **기록 날짜 / 주제:** 기록 시점과 일반적인 글쓰기 문제.
- **합성 상황:** 독자·판단 목적·문서 유형을 설명하는 짧은 가상 상황.
- **문제 문장 또는 구조:** 새로 만든 부족한 예시.
- **피드백과 독자 영향:** 무엇이 불명확하며 어떤 판단을 방해하는가?
- **수정 예시:** 문제를 해결하는 합성 문장 또는 구성. 관측하지 않은 사실을 실제 결과로 쓰지 않는다.
- **교훈 / 적용 범위 / 반례:** 일반화할 내용과 적용하지 말아야 할 조건.
- **관련 규칙:** [SKILL.md](../SKILL.md)의 해당 핵심 규칙.
- **반복 여부 / 상태:** 독립 사례에서 반복되었는지와 `기록`, `참고 사례`, `규칙 승격` 중 상태. 합성 예시 자체는 실제 반복의 증거가 아니다.

## 규칙으로 승격하는 절차

1. 새 사례를 기존 규칙과 대조한다. 이미 설명되는 교훈이면 규칙을 늘리지 말고 이해를 돕는 참고 사례로 다룬다.
2. 독립적인 문서나 피드백에서 같은 문제가 반복될 때 적용 범위와 반례를 검토한다. 비공개 원자료를 공개 로그에 붙이지 않는다.
3. 분야가 달라도 필요한 행동을 구체적으로 설명할 수 있는 교훈만 [SKILL.md](../SKILL.md)의 짧은 규칙으로 승격한다. 특정 유형에만 필요한 긴 설명은 참고 자료에 둔다.
4. 체크리스트와 사례가 새 규칙에 맞는지 확인한다. 사례 설명은 [피드백 사례](feedback-cases.md)로 옮기고 로그에는 승격 이유와 링크만 남겨 내용의 중복을 줄인다.
5. 사용자에게 보이는 변경마다 패키지의 `changelog.d/<issue>-<slug>.md`를 추가한다. 이슈 없는 허용된 직접 변경은 `changelog.d/direct-<slug>.md`를 쓴다. `### Added`, `### Changed`, `### Documentation` 등 저장소가 허용하는 섹션 아래 변경 내용을 bullet로 쓴다. 공용 `CHANGELOG.md`를 직접 수정하지 않는다.
6. 변경한 skill·참조 링크·패키지 메타데이터를 검증하고 공개 정보 검사를 통과시킨다. 실행한 검사와 미확인 항목을 보고한다.

## 기록

아직 추가 피드백 항목은 없다. 초기 합성 사례는 [피드백 사례](feedback-cases.md)에 있다. 이 로그를 채우려고 관측하지 않은 피드백이나 반복 횟수를 만들어 넣지 않는다.
